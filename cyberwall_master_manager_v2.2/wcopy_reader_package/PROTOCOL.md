# Протокол, используемый этим модулем

Основание — успешный аппаратный лог пользователя от 25.09.2026:
wCopy NSR109-HIDIC V806N, VID 2518, PID 6018, HID interface 0.
Поддержка других прошивок/клонов аппаратно не подтверждена.
Это описание реализованного обмена, а не полная спецификация производителя.

## Транспорт HID

Запись HIDAPI: 65 байт. Первый байт 00 — Report ID, затем 64 байта отчёта.
Чтение в успешном логе: 64 байта без Report ID. Парсер также принимает
65-байтовый ответ с нулевым Report ID.

| Поле внутри 64-байтового отчёта | Запрос | Ответ |
|---|---|---|
| Байт 0 | 01 | 02 |
| Байт 1 | Длина значимой части N | Длина значимой части N |
| Байты 2–3 | Номер запроса, little-endian | Номер запроса OR 1 |
| Байты 4…N−3 | Полезная нагрузка | Полезная нагрузка |
| Байт N−2 | Контрольная сумма | Контрольная сумма |
| Байт N−1 | FE | FD |
| Остаток до 64 байт | Нулевое заполнение | Заполнение не относится к данным |

N = длина полезной нагрузки + 6.
Контрольная сумма = `(~sum(report[0:N-2])) & 0xFF`.
Номера запросов: 0, 2, 4, …, с переполнением по 16 битам.
В новой сессии начинаем с 0. Ответ с другим номером пропускается в пределах
тайм-аута; повреждённый пакет завершает операцию ошибкой.

## Последовательность чтения

Инициализация — самостоятельная полезная нагрузка:
`FF 00 9A 5A A5 54 69 61 6E`. Ожидаемый ответ — `00`.

Остальные команды оборачиваются в:
`FF 00 00 00 Lc D4 <команда>`, где `Lc = 1 + len(команда)`.
Ответ начинается с `D5 <код команды + 1>`.
В реальном логе присутствует завершающий статус APDU `90 00`.

| Этап | Команда после D4 | Ответ после D5 и кода ответа |
|---|---|---|
| Выключить поле | 32 01 00 | 90 00 |
| Включить поле | 32 01 01 | 90 00 |
| Ограничить повторы поиска | 32 05 00 01 02 | 90 00 |
| Найти ISO14443A | 4A 01 00 | count, target, ATQA(2), SAK, UIDlen, UID, 90 00 |
| Авторизация | 40 01 60 01 + FF×6 + последние 4 байта UID | status, 90 00 |
| Чтение блока 1 | 40 01 30 01 | status, данные(16), 90 00 |

После выключения и после включения поля выдерживается по 50 мс.
В коде обмена 40 параметр 01 — номер цели; 60 — ключ A; следующий 01 — блок.
Статус обмена `00` означает успешную операцию. Сырые ненулевые статусы
передаются вызывающему коду без предположения о единственной причине сбоя.
Первоначально поддержанный вариант отсутствия карты: `00 90 00` (модельный тест).
В аппаратном тесте без карты пользователь получил тело `63 00` после `D5 4B`.
С версии 1.0.1 этот точный вариант на этапе поиска также вызывает NoCardError
со status=0x6300. Это трактовка для данной прошивки, а не универсальное
значение 6300: неуспешный поиск возможен и при физически присутствующей карте.

В конкретном тесте UID = C3 D7 C8 33, ATQA = 00 04, SAK = 08.
Модуль допускает UID длиной 4 или 7; для авторизации использует последние
4 байта. Аппаратный лог подтверждает вариант с 4-байтовым UID.
Допускаемые SAK: 08, 18, 09, 88; это фильтр реализации, а не обещание
совместимости со всеми картами с этими значениями.

Парсер допускает ответы без завершающего APDU-статуса при точном совпадении
ожидаемой длины, однако физически проверены ответы с `90 00`.
Нельзя просто удалять последние `90 00` по совпадению: это могут быть байты
самого блока. Сначала проверяется полная ожидаемая длина.

## Число и события

После успешного чтения данные блока имеют длину ровно 16 байт.
Число = unsigned big-endian от `block[8:16]`, диапазон 0…2^64−1.

События создаются на стороне ПК повторением полного чтения. Протокол
аппаратных push-уведомлений здесь не используется. Последний успешный UID
сохраняется до другого успешного UID либо двух последовательных ответов
«нет карты». Транспортные ошибки его не сбрасывают.

## Запись (версия 1.1.0)

После исходного чтения и без смены выбранной цели отправляется:
`FF 00 00 00 15 D4 40 01 A0 01 <16 байт блока>`.
Ожидаемый ответ: `D5 41 00`, с необязательным APDU-статусом `90 00`.
Затем повторяется полная последовательность чтения (с RF reset), с продолжением
номеров HID-запросов в том же USB-сеансе. Сравниваются UID и весь блок.
Команда записи не повторяется автоматически.

Код `A0` и формат 16-байтовой записи взяты из NXP PN532 User Manual,
UM0701-02, раздел InDataExchange, стр. 130:
https://www.nxp.com/docs/en/user-guide/141520.pdf
Это основание PN-совместимой команды; оно не подтверждает аппаратную
работу записи на конкретной прошивке wCopy. HID-обёртка и чтение основаны
на ранее успешном логе, новая запись проверена только модельными тестами.

Ключи, access bits и заводской UID модуль не изменяет.


## Свет/звук (история версии 1.2.0; актуальные результаты ниже)

В предоставленном nfcPro_x64(1).exe функция VA 0x140045BA0 формирует
`FF 00 40 50 04 T 01 01 01`, где T = max(1, (uint16_argument // 10) & 255).
Функция вызывается через VA 0x140033A30, в том числе после операций с картой.
Версии 1.2.0–1.4.2 использовали T=1; с 1.4.3 beep() использует T=5. Единицы длительности для этой прошивки аппаратно
не измерены. Программа производителя не проверяет семантику ответа этой команды.

Для цветов используется формат Bi-color LED and Buzzer Control из ACS ACR122U API,
раздел 6.2 и Appendix E:
https://www.acs.com.hk/download-manual/419/API-ACR122U-2.04.pdf
Здесь совпадение формата с командой nfcPro — основание для проверки, а не
доказательство полной совместимости wCopy с ACR122U.

- красный: `FF 00 40 0D 04 00 00 00 00`;
- зелёный: `FF 00 40 0E 04 00 00 00 00`;
- выключить оба: `FF 00 40 0C 04 00 00 00 00`.

Эти команды передаются непосредственно внутри HID-обёртки, без D4.
По ACS ответы `90 00`…`90 03` описывают LED, но на проверенном wCopy
это не подтверждено: 90 01 приходит при разных реальных цветах. Код также допускает
vendor-ответ `00`. Другие ответы вызывают FeedbackError. Реальный формат
ответа на этой прошивке нужно проверить feedback_test.py, который выводит
ответы без предположения об их значении.

После каждого успешного опроса/ответа «нет карты» watch с feedback=True
отправляет состояние LED. Сигнал отправляется только при новом CardPresented.
Сигнал идёт перед цветом: последняя команда задаёт окончательный цвет.
При сбое индикации дальнейшие команды индикации отключаются до перезапуска,
чтение продолжается. Изменений памяти или конфигурации ключей карты нет.

SHA-256 исследованного nfcPro: `24cb7571e5654e42d1ed2da73295f6bc2473e0dc6b5c36c3a5cccfb5f9a9fef1`.


## Разделение API (1.3.0)

`set_led(color)` отправляет ровно одну FF 00 40 <mask> команду.
`beep()` отправляет ровно одну FF 00 40 50 04 01 01 01 01 команду, без
последующей установки цвета. Это разделение на уровне программы, а не
гарантия независимости выходов прошивки.

`read_card`, `read_card_number`, `write_card_number` не вызывают индикацию.
Новый `watch_example` использует `watch_cards(report_state=True)` и вызывает
публичные функции индикации сам. CardState выдаётся на каждом успешном
опросе/отсутствии с debounce, чтобы сохранить прежнюю частоту команд LED.
Дополнительный beep в наблюдении по умолчанию отключён по результатам
аппаратного теста пользователя. В write_example beep вызывается после
подтверждённой записи; её успех не отменяется ошибкой индикации.

Самостоятельный feedback_test у пользователя не дал эффекта при ответах
90 01 на все команды. Поэтому ответ не трактуется как доказательство
физического состояния LED. Позднее пользователь подтвердил короткий писк после записи с T=1;
результаты расширенных проверок приведены ниже.

## Аппаратные результаты 11.10.2026 и API версии 1.4.3

Основание: indication_20261011_020216_224891.json и одноимённый .log,
библиотека 1.4.2, Python 3.14.7, Windows. Наблюдения цвета/звука записал пользователь;
USB-ответы не являются измерением физического состояния.

| Опрос | Реальный эффект |
|---|---|
| A: без дополнительного действия | Всегда красный, без писка |
| B: red/green по карте | Красный без карты, зелёный с картой, штатный писк |
| C: только открыть/закрыть HID | Всегда красный, без писка |
| D: пауза около 52 мс | Всегда красный, без писка |
| E/F/G: всегда red / green / off | Все три — как B, независимо от маски |

Поэтому set_led сохраняется и вызывается в watch после каждого опроса, включая
«нет карты». Это проверенная последовательность для штатной индикации;
минимальная частота и внутренний механизм пока неизвестны. Удалять эти вызовы
на основании отсутствия прямого управления цветом нельзя.

Одиночные команды после INIT, после чтения в том же HID-сеансе и после чтения
в новом HID-сеансе не дали видимого эффекта; ответы всегда 90 01. После закрытия
сеанса реакция на прикладывание/снятие оставалась штатной. Опыт без INIT
прерван ошибкой USB write -1/65, его результат по поддержке команды неопределён.

Для отдельного писка получены:

| T | TX→RX | Наблюдение |
|---|---|---|
| 1 | 25 мс | Очень короткий |
| 3 | 47 мс | Длиннее, но короткий |
| 5 | 69 мс | Близкий к штатному |
| 10 | 122 мс | Очень похож на штатный |

Все ответы 90 01; замеченного изменения LED нет. TX→RX — время обмена,
не непосредственное измерение длительности звука; около 10–11 мс прироста
на единицу T. Не переносим единицы 100 мс из документации ACR122U на wCopy.

Повторный статический разбор nfcPro подтвердил: функция VA 0x140045BA0
формирует FF 00 40 50 04 T 01 01 01. Все 79 найденных прямых вызовов обёртки
VA 0x140033A30 передают 50 (T=5); прямой вызов VA 0x14003E65E передаёт 100
(T=10). Внутри деление uint16 аргумента на 10, затем младший байт, ноль заменён 1.
Фиксированные маски 0D/0E/0C в исследованном пути не найдены; они добавлены
по аналогии с ACS, а не извлечены из программы производителя.

В API 1.4.3 beep(*, t=5, ...) принимает целое 1..255, проверяет до открытия USB
и подставляет только байт T. Bool, дробные, ноль и выход за диапазон запрещены.
Комбинированный set_reader_feedback(..., beep=True) тоже использует default T=5.
В watch EXTRA_BEEP=False, в write SUCCESS_BEEP_T=10. Сигнал записи вызывается
только после подтверждения UID и всего блока обратным чтением; ошибка сигнала
не отменяет результат записи. T=10 проверено после чтения; окончательная проверка
нового примера после реальной записи остаётся аппаратной задачей пользователя.
